# Tenxyte — Patch : permissions RBAC exigées par des vues mais jamais injectées

**Statut** : à appliquer sur le paquet `tenxyte` (upstream).
**Versions affectées** : au moins `0.9.5` (installée ici) **et** `0.9.6.4.2` (source dans `_docs/tenxyte/`). Les deux portent exactement le même défaut, aux mêmes emplacements.
**Sévérité** : haute pour l'exploitation — deux endpoints d'administration sont **inatteignables par tout le RBAC**, y compris le rôle `super_admin`. Seul `is_superuser=True` (contournement Django) passe, et encore : pas partout (voir § 4.2).

Découvert en branchant un back-office sur `/api/v1/auth/admin/*` : la section « Comptes & Sécurité » rendait `403` sur les Logs d'audit et l'édition d'un utilisateur, avec un compte pourtant porteur du rôle `super_admin`.

---

## 1. Résumé

`@require_permission("<code>")` (cf. `tenxyte/decorators.py`) résout la permission **uniquement** via `User.has_permission()` — lequel ne consulte que des lignes `Permission` réelles (rôles + permissions directes + hiérarchie parent/enfant). Il n'y a **aucun** contournement `is_superuser` dans ce chemin.

Conséquence : **tout code de permission référencé par un décorateur mais absent de `DEFAULT_PERMISSIONS` (et sans ancêtre injecté) est un mur `403` définitif**, quel que soit le rôle.

Deux codes sont dans ce cas :

| # | Code exigé | Vue(s) | Code réellement injecté par `tenxyte_seed` | Impact |
|---|---|---|---|---|
| **1** | `audit.view` | `AuditLogListView`, `AuditLogDetailView` (`views/security_views.py`) | *(aucun — ni `audit.view`, ni ancêtre `audit`)* — les vues sœurs du **même fichier** utilisent `security.view` | `GET /admin/audit-logs/` et `GET /admin/audit-logs/<id>/` → **403 pour 100 % des utilisateurs RBAC**, `super_admin` compris |
| **2** | `users.update` | `UserDetailView.patch` (`views/user_views.py`) | `users.edit` (seul groupe CRUD à ne pas utiliser le verbe `.update`) | `PATCH /admin/users/<id>/` → **403 pour les rôles `admin` et `super_admin`** (le parent `users` couvrirait `users.update` par hiérarchie, mais ni `admin` ni `super_admin` ne détiennent le *parent*, seulement des feuilles / `__all__` qui n'inclut pas une ligne inexistante) |

Vérification exhaustive effectuée : ce sont les **deux seuls** codes concernés. Tous les autres `@require_permission(...)` du paquet (`applications.*`, `permissions.*`, `roles.*`, `users.{view,ban,lock,delete}`, `dashboard.view`, `gdpr.{admin,process}`, `security.view`, `system.*`, `content.*`) sont bien injectés. Les permissions organisationnelles (`org.members.*`) relèvent d'un système séparé (`OrganizationRole.permissions` + `initialize_system_roles()`) et sont cohérentes.

## 2. Bug 1 — `audit.view` (jamais injecté)

### 2.1 Constat

`views/security_views.py` contient 7 vues. **5** utilisent `security.view` ; **2** utilisent `audit.view` :

| Ligne (0.9.5 & 0.9.6.4.2) | Vue | Décorateur |
|---|---|---|
| 59 | `AuditLogListView.get` | `@require_permission("audit.view")` ⟵ |
| 84 | `AuditLogDetailView.get` | `@require_permission("audit.view")` ⟵ |
| 122 | `LoginAttemptListView.get` | `@require_permission("security.view")` |
| 164 | `BlacklistedTokenListView.get` | `@require_permission("security.view")` |
| 215 | `BlacklistedTokenCleanupView.post` | `@require_permission("security.view")` |
| 254 | `RefreshTokenListView.get` | `@require_permission("security.view")` |
| 316 | `RefreshTokenRevokeView.post` | `@require_permission("security.view")` |

`security.view` **est** dans `DEFAULT_PERMISSIONS` — description : *« Can view audit logs, login attempts, tokens »* (elle décrit littéralement toute la surface `security_views.py`).
`audit.view` n'y est **pas**, et il n'existe pas de parent `audit` — donc `has_permission("audit.view")` fait `Permission.objects.get(code="audit.view")` → `DoesNotExist` → `False`. Mur.

### 2.2 Correctif recommandé (aucune migration, aucun nouveau code de permission)

Aligner les 2 vues restantes sur `security.view` comme leurs sœurs.

**`src/tenxyte/views/security_views.py`**

```diff
@@ AuditLogListView.get  (ligne ~59)
-    @require_permission("audit.view")
+    @require_permission("security.view")
     def get(self, request):

@@ AuditLogDetailView.get  (ligne ~84)
-    @require_permission("audit.view")
+    @require_permission("security.view")
     def get(self, request, log_id):
```

### 2.3 Documentation à corriger en même temps

Les docs référencent `audit.view` pour **cinq** endpoints (dont login-attempts et tokens, alors que le code y utilise déjà `security.view`) — la doc a dérivé, il faut la ramener sur `security.view` partout dans le bloc sécurité :

| Fichier | Lignes |
|---|---|
| `docs/en/admin.md` | 100, 101 (`audit.view` → `security.view`) |
| `docs/fr/admin.md` | 100, 101 |
| `docs/en/endpoints.md` | 79-84 (sommaire) + 3104, 3149, 3184, 3222, 3280 (titres de section + ancres) |
| `docs/fr/endpoints.md` | idem |

> `admin.md` mentionne aussi des codes fantômes jamais utilisés dans le code ni injectés : `tokens.view`, `tokens.revoke`, `gdpr.view`. À supprimer / remplacer par les vrais (`security.view`, `gdpr.admin`) pour éviter de futures confusions.

### 2.4 Alternative (si `audit.view` doit rester un code public)

Si tu préfères garder `audit.view` comme code documenté distinct :

1. `views/security_views.py` : ne rien changer.
2. `management/commands/tenxyte_seed.py`, dans `DEFAULT_PERMISSIONS`, section « Dashboard & Security » :
   ```python
   {"code": "audit.view", "name": "View Audit Logs",
    "description": "Can view the audit log", "parent": "security.view"},
   ```
   *(ou `parent` = un nouveau groupe `audit`, ou `system`.)*
3. Migration de données (cf. § 5) pour l'injecter dans les bases existantes.

**Recommandation : § 2.2.** `security.view` existe déjà, décrit exactement le besoin, et 5 vues sur 7 l'utilisent. Ajouter `audit.view` reviendrait à avoir trois codes quasi synonymes (`audit.view`, `system.audit`, `security.view`).

## 3. Bug 2 — `users.edit` vs `users.update`

### 3.1 Constat

Les quatre groupes CRUD de l'admin utilisent tous le verbe `.update`… sauf `users` :

| Groupe | `DEFAULT_PERMISSIONS` | Décorateur des vues |
|---|---|---|
| `roles` | `roles.update` | `roles.update` ✅ |
| `permissions` | `permissions.update` | `permissions.update` ✅ |
| `applications` | `applications.update` | `applications.update` ✅ |
| **`users`** | **`users.edit`** | **`users.update`** ❌ |

- `views/user_views.py` : `UserDetailView.patch` → `@require_permission("users.update")` (ligne ~550-551), et la docstring de la vue dit *« Réservé aux admins (permission users.update) »*.
- `decorators.py` : les exemples de docstring utilisent aussi `users.update` (`@require_any_permission(['users.create', 'users.update'])`).
- `management/commands/tenxyte_seed.py:40` : `{"code": "users.edit", ...}`.
- `DEFAULT_ROLES` → rôle `admin` (`tenxyte_seed.py:216`) : liste `"users.edit"`.

Le parent `users` est injecté, donc un porteur du **parent** `users` obtient `users.update` par hiérarchie. Mais :
- le rôle `admin` détient la **feuille** `users.edit`, pas le parent → `PATCH` refusé ;
- le rôle `super_admin` reçoit `permissions.set(Permission.objects.all())` **au moment du seed** → `users.update` n'étant pas une ligne, il ne l'a jamais.

### 3.2 Correctif recommandé — renommer `users.edit` → `users.update`

Verbe unifié avec les trois autres groupes, et alignement sur ce que les vues + docstrings + docs attendent déjà.

**`src/tenxyte/management/commands/tenxyte_seed.py`**

```diff
@@ DEFAULT_PERMISSIONS  (ligne ~40)
-    {"code": "users.edit", "name": "Edit Users", "description": "Can edit user information", "parent": "users"},
+    {"code": "users.update", "name": "Update Users", "description": "Can update user information", "parent": "users"},

@@ DEFAULT_ROLES → rôle "admin"  (ligne ~216)
-            "users.edit",
+            "users.update",
```

**Docs** : `docs/en/rbac.md:430` et `docs/fr/rbac.md:430` — table « Codes de Permission Intégrés » :

```diff
-| `users.edit` | Edit user information |
+| `users.update` | Update user information |
```

*(grep large conseillé : `rg -n "users\.edit" docs/ src/` — il ne doit rester aucune occurrence après patch.)*

### 3.3 Alternative (zéro migration)

Changer la vue au lieu du seed :

```diff
@@ src/tenxyte/views/user_views.py  UserDetailView.patch  (~550)
-    @require_permission("users.update")
+    @require_permission("users.edit")
```

… et corriger la docstring + les exemples de `decorators.py`.

**Recommandation : § 3.2.** `.update` est déjà la convention établie (3 groupes sur 4) et le nom présent dans les vues. Renommer une seule permission legacy est moins coûteux que perpétuer l'exception.

## 4. Constats secondaires (non bloquants — à ta main)

### 4.1 `_create_roles` ré-affecte les permissions même sans `--force`

`tenxyte_seed._create_roles()` appelle `_safe_set_permissions(role, ...)` **inconditionnellement** (hors du bloc `if force`). Donc un `tenxyte_seed` de routine **écrase** les permissions de tout rôle dont le `code` figure dans `DEFAULT_ROLES` — y compris si un intégrateur les avait ajustées à la main. C'est peut-être voulu (le seed fait autorité), mais ce n'est pas ce que « idempotent, ne recréera pas de doublons » laisse entendre dans la doc. À clarifier, ou à borner au `--force`.

Bon côté : c'est ce qui fait qu'un simple `tenxyte_seed` (sans `--force`) après le patch **répare** le rôle `admin` et le rôle `super_admin` des installations existantes — seule la ligne `Permission` `users.edit` orpheline reste (cf. § 5).

### 4.2 `has_permission()` n'a pas de court-circuit `is_superuser`

`docs/*/rbac.md` : *« Un super-utilisateur contourne automatiquement toutes les vérifications de permissions RBAC. »*
`models/auth.py` :
- `has_perm(self, perm)` → `return self.is_superuser or self.has_permission(perm)` ✅
- `has_permission(self, code)` (celui qu'appelle `@require_permission`) → **aucun test `is_superuser`** ❌

Donc un `is_superuser=True` se fait aussi refouler par `@require_permission("audit.view")` tant que Bug 1 n'est pas corrigé, contrairement à la doc. Deux options :
- ajouter `if getattr(self, "is_superuser", False): return True` en tête de `has_permission()` (aligne le code sur la doc, comportement le moins surprenant) ;
- ou corriger la doc pour dire que seul l'admin Django (`has_perm`) est court-circuité, pas l'API RBAC.

### 4.3 `super_admin` / `__all__` est résolu au moment du seed

`_create_roles` : `all_permissions = list(Permission.objects.all())` **une fois**, puis `role.permissions.set(all_permissions)`. Toute permission créée **après** le seed (par un intégrateur, un autre paquet, ou… un futur `DEFAULT_PERMISSIONS` élargi sans re-seed) échappe à `super_admin`. C'est exactement le mécanisme qui a masqué les Bugs 1 & 2 (les vues référençaient des codes que `__all__` ne pouvait pas contenir).

Piste de robustesse : traiter `super_admin` comme `is_superuser` dans `has_permission()` —
```python
def has_permission(self, permission_code):
    if getattr(self, "is_superuser", False):
        return True
    if self.roles.filter(code="super_admin").exists():
        return True
    ...
```
… ou un flag `Role.grants_all = BooleanField(default=False)` posé sur `super_admin`, consulté dans `_get_effective_permission_codes()` / `has_permission()`. Cela rend `super_admin` insensible au timing du seed et aux extensions downstream.

### 4.4 Filet CI qui aurait tout attrapé

Aucun test ne vérifie que les codes des décorateurs existent dans `DEFAULT_PERMISSIONS`. Proposition (à ajouter à la suite de tests du paquet) :

```python
# tests/test_permission_contract.py
import ast
import re
from pathlib import Path

import pytest

from tenxyte.management.commands.tenxyte_seed import DEFAULT_PERMISSIONS

SRC = Path(__file__).resolve().parent.parent / "src" / "tenxyte"
SEEDED = {p["code"] for p in DEFAULT_PERMISSIONS}
DECORATOR_RE = re.compile(
    r'@require_(?:any_|all_)?permissions?\(\s*(\[[^\]]*\]|["\'][^"\']*["\'])'
)


def _covered(code: str) -> bool:
    """Injecté directement, ou via un ancêtre injecté (hiérarchie)."""
    if code in SEEDED:
        return True
    parts = code.split(".")
    return any(".".join(parts[:i]) in SEEDED for i in range(1, len(parts)))


def _referenced_codes():
    for path in SRC.rglob("*.py"):
        text = path.read_text(encoding="utf-8")
        for m in DECORATOR_RE.finditer(text):
            for code in re.findall(r'["\']([^"\']+)["\']', m.group(1)):
                yield code, path


@pytest.mark.parametrize(
    "code,path",
    sorted({(c, str(p)) for c, p in _referenced_codes()}),
)
def test_decorator_permission_is_seeded(code, path):
    assert _covered(code), (
        f"@require_permission({code!r}) dans {path} n'est ni dans "
        f"DEFAULT_PERMISSIONS ni couvert par un ancêtre injecté — "
        f"endpoint inatteignable par le RBAC."
    )
```

*(Équivalent possible pour `@require_role` vs `DEFAULT_ROLES` — sur ce paquet, seule la doc utilise un `manager` fantôme, aucun décorateur réel, donc non urgent.)*

## 5. Migration pour les installations existantes

Après patch du code, les **nouvelles** installations sont correctes via `tenxyte_seed`. Pour les bases déjà déployées :

### 5.1 Le chemin simple

```bash
python manage.py tenxyte_seed          # ré-injecte users.update, ré-affecte admin + super_admin
```

Ça suffit pour restaurer les rôles. Reste la ligne `Permission(code="users.edit")` orpheline (inoffensive, mais elle traîne, et d'éventuelles permissions **directes** `users.edit` sur des utilisateurs ne sont pas transférées).

### 5.2 Migration de données propre (recommandée, à livrer dans le paquet)

`src/tenxyte/migrations/00XX_rename_users_edit_permission.py` :

```python
from django.db import migrations


def forward(apps, schema_editor):
    Permission = apps.get_model("tenxyte", "Permission")
    old = Permission.objects.filter(code="users.edit").first()
    if not old:
        return
    new = Permission.objects.filter(code="users.update").first()
    if new is None:
        # Renommer en place : conserve les M2M (rôles + permissions directes).
        old.code = "users.update"
        old.name = "Update Users"
        old.description = "Can update user information"
        old.save(update_fields=["code", "name", "description"])
        return
    # `users.update` existe déjà (créé par un tenxyte_seed post-patch) :
    # basculer les liens de l'ancienne vers la nouvelle, puis supprimer.
    RoleThrough = Permission.roles.through
    RoleThrough.objects.filter(permission_id=old.id).exclude(
        role_id__in=RoleThrough.objects.filter(permission_id=new.id).values("role_id")
    ).update(permission_id=new.id)
    DirectThrough = apps.get_model("tenxyte", "User").direct_permissions.through
    DirectThrough.objects.filter(permission_id=old.id).exclude(
        user_id__in=DirectThrough.objects.filter(permission_id=new.id).values("user_id")
    ).update(permission_id=new.id)
    RoleThrough.objects.filter(permission_id=old.id).delete()
    DirectThrough.objects.filter(permission_id=old.id).delete()
    old.delete()


def backward(apps, schema_editor):
    Permission = apps.get_model("tenxyte", "Permission")
    p = Permission.objects.filter(code="users.update").first()
    if p and not Permission.objects.filter(code="users.edit").exists():
        p.code = "users.edit"
        p.name = "Edit Users"
        p.description = "Can edit user information"
        p.save(update_fields=["code", "name", "description"])


class Migration(migrations.Migration):
    dependencies = [("tenxyte", "0018_user_must_change_password")]  # adapter au HEAD
    operations = [migrations.RunPython(forward, backward)]
```

> Vérifie les vrais `related_name` (`Permission.roles`, `User.direct_permissions`) sur ta branche — ici pris de `models/auth.py` (`roles__users`, `users_direct` dans les `Q(...)` de `has_permission`, donc l'accès inverse est `permission.roles` / `permission.users_direct`).

Pas de migration nécessaire pour Bug 1 si tu prends l'option § 2.2 (changement de décorateur uniquement).
